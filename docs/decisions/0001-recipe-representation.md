# 0001：批量配方的表示方式（物化 / 紧凑配方族）

- 状态：接受。路线已确定；紧凑族实现尚未开始，选族依据与具体性能阈值待测量并在实现前记录。
- 日期：2026-10-29。作者：Masson。
- 替代/被替代关系：无。

## 背景与约束

初始比较时，九张大图的初步报告列出几十万行未匹配项：extruder 约 12.4 万、mixer 约 6.2 万、bath 约 5.7 万、smelter/melter 约 2.8 万、boxinator/unboxinator 约 3.4 万、generifier/crusher 约 2.1 万。这些是旧比较口径下的差异，不是已证明的待新增配方数量。名称归一、真实身份缺失、注册缺失、参数差异及合理排除须拆开；“约四成换名”“形态/名字占四分之三”不能据此推导最终物化总量。

2026-10-29 Forge 开发服务端日志记录了约 59.6 万条静态行：

| 指标 | 已记录值及口径 |
| --- | --- |
| 机器配方注册（commonSetup 合计） | 34.6 s；其中 `OreProcessingRecipeLoader` 16.3 s、`PartRecipeLoader` 8.3 s |
| 数据包 overlay 基线恢复 | 233 ms / 575,990 行；不是整个 `/reload` 耗时 |
| `RecipeDump` 写盘 | 22 s，仅开发导出 |
| 服务端 `Done` 日志 | 17.7 s，属于该日志计时阶段，不能当作进程启动总时间，也不能与上述阶段直接相加 |

现有实现的约束：

- `RecipeMap` 物化 `Recipe`、物品/流体栈及数组，维护输入索引；`RecipeLookupTable` 另持有快照与候选缓存。原生输入查找有索引，别名回退仍可能遍历快照；不能把所有查找都视为常数开销。
- `addRecipes` 用临时输入锚点减少碰撞扫描，仍逐行构造和检查。注册时间须剖析，不能仅凭行数认定一定线性或一定超线性。
- overlay 对每张图首次捕获基线，随后恢复并重建受 tags 管理的行，再执行数据包删除与新增。基线保存配方引用，不深复制所有配方；恢复仍有 O(行数) 扫描及临时集合。
- JEI/EMI 当前遍历静态 `mRecipeList`。动态行不在列表中，默认不会进入查看器、基线或逐行 dump。
- 静态未命中后调用动态扩展，可以复用为族查找入口；是否可保持原来的匹配顺序和碰撞规则须逐族证明，不因“整图是族”就必然重写整张图。
- 输入准入、附属 API 查询与流体容量元数据也依赖静态表。只提供动态 `findRecipe` 不构成完整接入。
- 两版本共享 Minecraft 源码由 Stonecutter 处理；`core` 只承载平台无关规则，不引入游戏对象。
- CrucibleCraft 的紧凑族及逐行覆盖报告证明了该方向值得参考，不证明 GT6CE 已实现或具备相同覆盖率。CC 为外部只读参照；实现按本仓边界重写。

当前尚无足以决策具体预算的配方留存堆、峰值分配、客户端查看器成本与冷/热查找数据。

## 备选与取舍

| 选项 | 收益 | 代价与适用边界 |
| --- | --- | --- |
| A：继续物化 | 复用当前匹配、overlay、查看器和工具；补齐小表、特例与不规则表成本最低 | 栈、索引、来源记录和查看器对象随行数增长；冷未命中及别名查找也可能昂贵。适合作为默认实现，但不承诺无限扩表 |
| B：全面紧凑族 | 规则能描述大量逻辑行，可减少常驻 Recipe 数量及重复构造 | 必须一次承担公共契约、修改层、工具与查看器适配成本。材料身份、索引、显示和缓存仍耗内存，不能承诺总内存恒定；不适合把不规则表强行规则化 |
| C：混合存储 | 保留 A 的默认路径，仅压缩收益明确的大而规则族，可逐族迁移 | 首个族仍要支付 B 的大部分基础设施成本；增加交互验证。采用同一行为语义、两种存储，避免形成两套配方规则 |
| D：先补身份 | 修复真实缺失的材料形态、流体与对象，可同时解除多个族的阻塞 | 属于依赖处理顺序，不能替代配方落地。仅改比较名称不会新增玩法；真实注册身份也可能使现有生成器直接新增可用行 |

## 已接受的决定

采用 **C 作为长期路线、A 作为默认、D 按配方族处理前置依赖**，不进行全面 B 改造。

1. 已具备身份的小表、不规则表和明确玩法缺口继续物化补齐。紧凑存储的公共契约和全局身份补齐均不是这些工作的硬前置。
2. 每个族先区分比较别名和实际注册缺口。补足本族需要的身份即可推进；共享身份集中处理，避免在各配方族里重复造对象。身份落地后须连同依赖配方及玩家查询验证闭环。
3. 仅当一个族可精确规则化，而且实测构造、留存、查找或查看器成本值得压缩时，才采用紧凑表示。行数是筛选信号，不设置一个未经测量的“超过 N 行必须紧凑”规则。
4. 紧凑存储先交付公共契约、度量方式及一个完整首族。根据数据选择 extruder 压缩现存大表，或 mixer 补齐较大覆盖缺口；以完整可界定的族为单位，不在只完成接口或少量代表行时视为完成。
5. 全图规范对账与问题清单、九张主要配方图的补齐、以及其余配方入口的闭环分别推进；存储优化不代替全图配方补齐。

### 两种存储必须共享的契约

- **行身份与匹配**：有稳定逻辑身份；物品/流体数量、presence 催化剂、NBT/组件、概率、时长、能耗、特殊参数及 flags 的语义一致。迁移保持既有匹配优先级、碰撞拒绝和特例；“静态优先”不能直接替代原有注册顺序的证明。
- **查找与枚举**：按需查找、输入/产物查询和有限逻辑域的完整枚举读取同一规则。逻辑计数是有效身份、约束与例外过滤后的行数。开发 dump 流式展开，不把枚举行灌入运行时缓存；缓存热度与淘汰不改变枚举、计数或输出。
- **修改层与 reload**：在基线规则之上沿用先删后加的语义。删除条件须作用于尚未生成的行；删除不能靠清除已缓存对象实现。撤回数据包并 `/reload` 恢复原基线；tags、材料别名或修改层变化统一使相关缓存与未命中缓存失效。
- **输入与容量**：族接入输入准入、附属查询和必要流体容量元数据；相关机器既能找配方，也能接收和容纳所需输入。
- **玩家可发现性**：JEI/EMI 对原版应展示的普通有效配方保留具体物品的配方/用途查询（R/U）、正确用量及关联产物，并保持源隐藏与条件展示语义。可以评估等价分组或按查询展开，但“只有代表行”或关闭大图不是默认交付方式。不得以降级玩家体验换取性能指标。
- **缓存与生命周期**：缓存有明确图级或全局预算，键包含影响匹配的身份/数据与规则代次；命中、未命中和淘汰后重建行为等价。基线、来源记录、查看器与导出不得偷偷重新持有全部逻辑行。

## 度量、落地与验证

紧凑存储的实现前先记录测试硬件、版本、JVM/堆设置、模组与数据包集合、族范围、已有基线及约定的绝对预算。预算至少覆盖注册/启动阶段、稳定留存与峰值内存、reload、冷/热查找、查看器加载与查询；具体数字待测量后约定，未测不能写成通过。

- 堆评估比较同环境下启用/禁用目标族或旧物化/新紧凑方式的增量，用直方图、留存对象分析及一致的采集时点区分配方、身份、索引、来源记录和查看器成本。全局堆占用除总行数再外推无效。
- 分开测量开发 dump、配方注册、基线恢复、完整 reload 和进程启动；导出可能扰动启动，不能拿不同开关的日志直接比较。
- 查找覆盖冷命中、热命中、无匹配、材料别名、冲突与缓存淘汰；记录 p50/p99 及工作集，不能只报告热缓存平均值。
- 查看器保持等价发现能力做对比。关闭图可用于诊断开销，不作为可交付的优化结果。
- 相对恶化超过 30% 仅作为回顾告警；是否通过由约定的绝对预算、正确性与发现能力共同决定，不能用这一比例作唯一门槛。

完整修改收敛后集中执行一次相关单平台检查，复用未受影响的结果；涉及平台专用代码、Stonecutter 分支、发布打包门禁或具体跨平台风险时，写明理由后补另一端的对应验证。全量展开对账证明首族覆盖与参数，集中行为回归证明匹配、修改层、失效、进料及查看器；不以抽样可用代替逐行证据，不把逐行 dump 等同于全部游戏行为已验证。
