# Stonecutter 文档模板

本页规定 Stonecutter 分类 README 与子样例的编写格式和验收要求；新增或修改分类文档时按本页执行。

## 分类索引样例

### 格式

````markdown
# <领域>

<一句话总结：这个领域处理什么差异，共同原因是什么>

## 子类型

| 子类型 | 说明 | 文档 | 关键词 |
| --- | --- | --- | --- |
| <子类型> | <一句话说明> | [<子类型>.md](<子类型>.md) | <关键词> |

## 其他话题

<可选：与方针的对应、边界、验证方式等>
````

### 要求

- 一句话总结写在标题下、`## 子类型` 之前，说明领域对象和共同原因；不写迁移过程、轮次或提交号。
- 一句话总结与 `## 子类型` 之间可以放一张版本对照表；对照表只列签名或格式差异，不展开例子。
- `## 子类型` 表固定四列：子类型、说明、文档、关键词；每行必须链接到一个子文档，文件名用小写连字符。
- 子类型按差异原因划分，不按文件或类名划分；一个子类型只对应一个子文档。
- 可选章节放在子类型表之后；不重复 `categories.md` 或其他领域的内容，直接链接。
- 分类 README 必须能从 `categories.md` 进入；新增、改名或删除子文档时同步 `categories.md` 的索引与关键词。
- `Parity` 是守卫页，不按本模板；其结构见 [Parity/README.md](Parity/README.md)。

## 子样例模板

### 格式

````markdown
# <子类型>

## 子原因

<为什么会出现这个 //? 分支：平台 API、类落点、注册归属、数据格式等>

## 例子

### 修复前

```java
//? if >=1.21.1 {
...
//?} else {
...
//?}
```

### 修复后

```java
...
```

### 为什么这么修复

- ...

### 其他可能的修复方式

- ...

相关链接：[issue #358](https://github.com/GregTech6CE/GregTech6/issues/358)
````

### 要求

- 必须落实和 Stonecutter 的关系：`## 子原因` 说明分支为什么存在（平台 API 运行时差异、类落点、注册归属、数据格式等），不能只写“代码不同”。
- 示例代码必须落实到 `//?`：`### 修复前` 展示真实的 `//?` 分支（含 `//? if ... {`、`//?} else {`、`//?}`），不能只贴普通 Java 代码或伪代码。
- 一个文件只包含一个样例：一个“修复前/修复后”对；同一子原因的其他例子另开文件，并在分类 README 中登记。
- `### 修复后` 展示分支消失或缩小后的代码；分支保留时必须写明保留原因、影响面和验证方式。
- `### 为什么这么修复` 说明行为或结构影响，以及为什么不属于平台 API 例外；属于例外时按 [unification-policy.md](unification-policy.md) 的四个条件逐条说明。
- `### 其他可能的修复方式` 至少列出一个被否决的方案和原因。
- 不写轮次、提交号或迁移过程；代码示例只保留与分支相关的片段，不复制大段源码。
- 新增或修改子文档后，同步分类 README 的表格和 `categories.md` 的关键词。
- 相关链接指向 issue #358 或具体 issue/PR。

## 验收

新增或修改文档后按以下清单逐项验收；需要独立验收时按同一清单复核。

1. 每个文件只有一个例子（一个“修复前/修复后”对），没有内嵌第二个例子。
2. 章节结构与同目录文档一致：标题、子原因、例子、修复前、修复后、为什么这么修复、其他可能的修复方式、相关链接。
3. 是“指导指南”而不是迁移笔记：不出现轮次编号、提交号、迁移过程叙述。
4. 中文风格与既有文档一致；没有口语化表达或生造词。
5. 代码示例与当前仓库代码事实一致；抽查相关目录或类的字段、方法名和分支条件。
6. 新增文档之间、与既有文档之间没有明显重复的子原因。
7. 分类 README 与 `categories.md` 的索引已包含新增或修改的文档。
