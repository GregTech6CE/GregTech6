# Stonecutter 文档模板

本页规定 Stonecutter 分类 README 与子样例的编写格式和验收要求。新增或修改分类 README 或子样例时按本页执行。

## 通用要求

1. 不写迁移过程、轮次或提交号。
2. 代码示例只保留与分支相关的片段，不复制大段源码。
3. 分类、子类型、子样例之间不重复。同一内容只在一层展开，其他层直接链接。
4. 可选章节放在后面。子样例一般不放可选章节，除非涉及的概念和话题十分重要和复杂，需要明确说明。
5. 章节结构与同目录文档一致。
6. 同步更新相关文档链接，包括 `categories.md`、分类 README 和子样例。
7. 使用相对链接，引用现存文件。
8. 中文风格与既有文档一致，没有口语化表达或生造词。
9. 代码示例与当前仓库代码事实一致，字段、方法名和分支条件可复核。

## 分类 README

### 模板格式

````markdown
# <分类>

<一句话总结：这个分类处理什么差异，共同原因是什么>

## 子类型

| 子类型 | 说明 | 文档 | 关键词 |
| --- | --- | --- | --- |
| <子类型> | <一句话说明> | [<子类型>.md](<子类型>.md) | <关键词> |

## 其他话题

<可选：与方针的对应、边界、验证方式等>
````

### 要求

- 一句话总结写在标题下、`## 子类型` 之前，说明分类对象和共同原因。
- 一句话总结与 `## 子类型` 之间可以放一张版本对照表。对照表只列签名或格式差异，不展开例子。
- `## 子类型` 表固定四列：子类型、说明、文档、关键词。每行必须链接到一个子样例，文件名用小写连字符。
- 子类型按差异原因划分，不按文件或类名划分。一个子类型只对应一个子样例。
- `Parity` 是守卫页，不按本模板。其结构见 [Parity/README.md](Parity/README.md)。

## 子样例

### 模板格式

````markdown
# <子类型>

## 子原因

<为什么会出现这个 //? 分支：平台 API、类落点、注册归属、数据格式等>

## 例子

### 修复前

```java
//? if >=1.21.1 {
...
//?} else {
...
//?}
```

### 修复后

```java
...
```

### 为什么这么修复

- ...

### 其他可能的修复方式

- ...

相关链接：<具体 issue/PR，例如 issue #358>
````

### 要求

- 必须落实和 Stonecutter 的关系：`## 子原因` 说明分支为什么存在（平台 API 运行时差异、类落点、注册归属、数据格式等），不能只写“代码不同”。
- 示例代码必须落实到 `//?`：`### 修复前` 展示真实的 `//?` 分支（含 `//? if ... {`、`//?} else {`、`//?}`），不能只贴普通 Java 代码或伪代码。
- 一个文件只包含一个子样例：一个“修复前/修复后”对。同一子原因的其他例子另开文件，并在分类 README 中登记。
- `### 修复后` 展示分支消失或缩小后的代码。分支保留时必须写明保留原因、影响面和验证方式。
- `### 为什么这么修复` 说明行为或结构影响，以及为什么不属于平台 API 例外。属于例外时按 [unification-policy.md](unification-policy.md) 的四个条件逐条说明。
- `### 其他可能的修复方式` 至少列出一个被否决的方案和原因。
- 相关链接指向具体 issue/PR。没有具体链接时可以省略。issue #358 只是示例，不是固定要求。

## 验收

先逐项验证 `## 通用要求`，以及分类 README 和子样例的具体要求，再检查以下未被这些要求覆盖的项目：

1. 分类 README：一句话总结、子类型表（四列）、子样例链接齐全。子类型按差异原因划分。
2. 子样例：子原因、修复前、修复后、为什么这么修复、其他可能的修复方式、相关链接齐全。
3. 每个文件只有一个例子（一个“修复前/修复后”对），没有内嵌第二个例子。
4. `### 修复前` 展示真实的 `//?` 分支，`### 修复后` 展示分支消失或缩小后的代码。
5. 分支保留时，写明保留原因、影响面和验证方式。
