# 01：建立基线与正确性对照

本计划把材料链路转成可重复观察和验证的对象，作为后续迁移的验收基础。状态：已实施并完成下述范围的基线验收；无前置计划。实际结果与已知差异见[基线报告](../../integration/material-baseline.md)，完整原始材料留在 `work/material-system-refactor/`。通用约束与检查代号见[总计划](README.md)。

## 目标与边界

交付“当前行为”“权威期望”“差异说明”三类可区分的结果。当前配方数量或材料数量不作为正确性结论。本阶段主要增加测试与调查证据；发现生产缺陷时先记录，由对应迁移阶段修复，不能在基线采集中顺手改变注册顺序。

## 先读与入口

- `core/src/main/java/gregtech/engine/material/GTMaterialRegistry.java`：定义、链接、别名、core 身份与附属安装阶段。
- `core/src/main/java/gregtech/content/material/MaterialDefinitions.java` 及 `content/data/generated/Material*`：事实写入点。
- `core/src/test/java/gregtech/content/material/MaterialTestFixture.java`、`MaterialCatalogTest.java`、`FuelParityTest.java`：已接入的 core 回归。

- `minecraft/src/main/java/gregtech/content/recipe/MachineRecipeBootstrap.java`、`MachineRecipeLifecycle.java`、`MachineRecipeOverlay.java`：生成、覆盖及重载。
- [parity](../../decisions/parity/README.md)、[JUnit](../validation/checks/junit.md)、[GameTest](../validation/checks/gametest.md)。

## 实施步骤

### 1. 固定调查环境与比较口径

1. 记录代码提交、已有工作区修改、两个节点、可选模组是否启用；不把他人未提交修改归入本计划。
2. 在无可选模组环境采集基线，另用 test source set 的附属夹具覆盖附属声明；不能因真实联动模组缺席而跳过宿主 SPI 路径。
3. 区分原始材料对象、`resolve()` 后材料与可用材料；快照以稳定注册身份表示链接，不使用内存地址、动态附属数值 ID 或哈希容器迭代顺序。
4. 把两个节点同名物品的成分和授权做交集比较；版本独有物品另列，不因物品总数不同直接判定失败。

交付：`work/material-system-refactor/` 中的环境说明和原始采集结果；可运行的纯快照归一化测试。

### 2. 定义精简快照

| 范围 | 必须比较的字段 | 归一化规则 |
| --- | --- | --- |
| 材料 | ID、注册名、别名、来源、原子与物性、燃料／灰烬、加工目标、组成与 divider | 按稳定身份排序；有语义的副产物顺序保留 |
| 形态 | prefix 身份、可生成性、单位重量、最终物品／方块 ID | 只记录实际候选与生成结果，不物化所有材料×所有 prefix |
| 物品成分 | 物品 ID、prefix、全部材料量、批量授权、来源与派生类型 | 无语义的组件集合按身份排序；主材料另列，避免排序改变含义 |
| 配方 | map、输入身份与数量、选择器／催化剂、输出、时长、EUt、运行期限制 | 语义签名保留槽位和角色，内部 unit 折叠单列 |

不要提交整份机器原始 dump。提交的期望文件只保留审阅过的稳定字段或代表性案例；其余全量结果留 `work/`。增加字段时说明它验证的外部行为，避免快照变成每次重构都要重录的实现副本。

### 3. 建立差异分类与数据校验

1. 枚举成分、分解、形态、UUM、加工目标表中的目标引用，分成有效、已停注、别名映射、真正悬空四类。
2. 对已停注行要求指向现有移除决策；不能把 issue 中的历史漂移数量直接录成永久允许数量。
3. 对未知悬空引用先输出带表名、材料身份与字段的失败证据。严格失败规则在清理或显式标注历史行后启用，避免首次开启校验就让正常启动全部失败。
4. 当前错误行为可由明确的“已知差异案例”记录；正确性断言只采用已核对依据的预期。测试保持可执行，不用禁用测试表达待办，也不以兼容快照覆盖正确性断言。

交付：有限、逐条解释的差异清单，以及能对新增非法引用报错的纯校验器；如当前非法行尚未修复，应明确本阶段未完成或把对应修复作为独立小变更先完成。

### 4. 接入最小运行期测试

优先扩展 `BlockPropertyTests` 的成分存在性检查；不能用该类替代材料链路测试。新增按材料领域命名的共享 GameTest，先覆盖：

- 普通铁／铜存储块：全部成分、材料量、批量回收与坩埚准入分别可观测。
- 72U 物品：记录当前计划与最终可查产物，显露是否截量。
- 复合工具头：注册表、物品实例与等价形态查询的差异可定位。
- 完好／部分损坏／耗尽工具、空容器／有内容物容器：拒绝或缩放原因可定位。
- 已凿形状的铸模与压模机模具：记录成分、形状状态和回收准入，承接 #351 关联的 #349、#350。现有 `MoldDropTests` 只证明掉落保留形状，不能证明坩埚或批量回收可用。
- 一种固体化合物与一种带流体输入的化合物：分解 map、输入与输出可查询。
- 数据包重载前后：同一固定样例可查询，拥有者和规则数量无累积。

若使用真实重载可能影响并行 GameTest，放入独立顺序批次并等待完成，再恢复夹具；仅调用内部 `rebuild()` 只能证明内部函数，不能宣称真实资源重载已验证。

## 独立验证与完成条件

检查集：D、F、J、C、G；若新增测试夹具改变生产打包配置，再加 B。测试源码必须实际由两个节点编译和执行。

| 验证项 | 通过条件 |
| --- | --- |
| 重复采集 | 同一节点两次干净启动的归一化结果一致；忽略项逐项有理由 |
| 权威期望 | 每条正确性案例有 parity 或固定 GT6 方法／数据依据；现代内容有明确项目规则 |
| 引用完整性 | 已知停注有分类；新增未知悬空、ID／name 矛盾、非法组件必须失败 |
| 负例有效 | 注入一个假材料引用或修改一条预期数量，测试确实失败；移除注入后恢复通过 |
| 游戏链路 | 两节点实际执行代表案例，首次启动与重载证据分开记录 |

本阶段结束时应能回答“后续改动改变了什么，哪些改变获得了依据”，并能直接运行已有测试获得相同结论。

## 拆分与失败处理

建议分成：纯归一化与引用校验、已知漂移清理、运行期快照与代表案例三个小变更。全局初始化测试不添加生产 reset 方法；优先复用单次初始化 fixture，确需测试独立生命周期时使用独立 JVM 的测试隔离机制。

因上游源码或游戏环境缺失导致无法核实时，写出具体缺口，保留已有检查结果；相应阶段保持未验收。基线测试失败本身是定位证据，不能通过删断言变成通过。

## 实施结果（2026-11-07）

- core 新增独立 JVM 材料／别名／prefix／引用投影、源表审计与逐行历史分类，测试附属经真实 ServiceLoader 安装；没有增加生产 reset；先独立删除形态表误抽取的 `rmaterial` 一行，再开启严格零未知引用校验。
- 共享 `MaterialBaselineTests` 包含 8 个材料领域用例，覆盖代表样例、test-source 材料 SPI 和独立顺序批次中的两次真实资源重载。
- 材料、物品／方块形态、成分、配方语义及 tag 成员采用排序投影；无序 tag 的展示代表单独归一化，不忽略输入集合。
- 当前行为、权威断言和差异清单已经分开。72U 金苹果截量、铜材的双平台差异、原生工具／压模具缺少成分、有形状铸模被拒、NeoForge Fermenter 重载差异均保留，未在本阶段修复生产行为。
- 检查、精确平台版本、负例和重复采集结果统一维护在[基线报告](../../integration/material-baseline.md#复现与执行记录)。后续阶段不能把更新观察数据当作正确性裁决。
