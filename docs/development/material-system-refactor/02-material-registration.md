# 02：统一材料注册与规范数据

本计划使材料身份与定义只有一条经过校验的安装路线，并把同一材料的静态事实收敛到规范目录。状态：已实施并完成下述范围；前置 [01](01-baseline.md) 已完成。目标类名用于描述拟议设计，实际命名遵循现有包与风格。

接口定稿前完成 [08-A](08-material-data-api.md#a确定薄视图与最小公共契约)，metadata 扩展与分类／组按 08-B 接入；[设计提议 0001](../../decisions/0001-material-data-api.md) 约束主材料只承载内在事实，来源与处理图通过查询服务提供。新公开模型不把 `Any*` 组当真实材料，旧内部对象在消费者迁完前保留适配。

## 目标与实际入口

实施前 `registerDefinition()`、`createMaterial()`、`installAddonMaterial()` 的约束不同，`MaterialFactories` 又直接创建材料。迁移已把这些入口收敛到 `MaterialRegistryState.install`，旧方法只保留受阶段约束的兼容转发。

需要同时跟踪：

- core 的 `engine.material.GTMaterialRegistry`、`MaterialDefinition`、`MaterialRegistryState`、`MaterialLinker`；
- `content.material.MaterialDefinitions`、`Materials` 及 `content.material.generated` 目录；
- `content.data.generated.GT6Materials`、`content.data.ImportedMaterialData`；
- `engine.addon.AddonMaterials` 的定义安装、共享声明合并、所有权、链接与发布；
- `content.data.MaterialGroups`、`AntimatterMaterials` 以及 `postInit()` 的追加事实；
- 公共 `api.addon.material` 声明和访问协议。

## 目标数据与阶段

规范目录以稳定名称和保留的内置 ID 标识材料；引用其他材料时保存稳定键，由链接阶段解析。逻辑上每种材料一条声明，可按元素、化合物、木材等分文件。先扩展并复用 `MaterialDefinition`，只有确实需要时才增加承载关联声明的类型，不引入第二种旁路注册模型。

主定义只承载身份、展示、物性／原子、基础属性与来源；组成与 divider、加工目标、燃料／灰烬、形态规则、工具和分解权限通过 `MaterialKey` 关联到独立附属域。03、06 负责将这些附属域进一步变成最终查询，本阶段先统一身份与数据归属。

定义安装、引用链接、最终校验应有清晰边界。现有链接会建立材料组，附属回调也可能进行合法操作，因此实施前先列这些调用：能预声明的移到定义阶段；确需链接时合成的组通过显式内部路线创建并接受同样身份校验。不得给普通调用者开放无限制创建窗口。

## 实施步骤

### 1. 整理身份与失败策略

1. 盘点所有创建、别名、replacement 与 re-registration 调用，区分历史同名覆盖和真正的材料等价关系；`setRegistration` 的语义不能直接按“重复材料”删除。
2. 把唯一性检查放在改变任意索引之前：名称、ID、别名、阶段失败时，名称索引、ID 索引与全量集合都保持原状。
3. 将 sentinel 的初始化、内置正 ID、附属宿主分配 ID 分别作为明确安装模式，共用名称和 ID 冲突校验。
4. 保留附属同名一致声明的既有合并契约；定义不一致时指出附属、字段和两份来源，不把它误报成普通重复内置材料。
5. 处理别名的规范名优先、历史反物质冲突等特例：保留有依据的规则，放进显式映射并测试；未声明的冲突报错，相同别名与目标重复安装可幂等。

交付：一个安装核心；旧创建方法只作为受约束的临时转发或移除，不再拥有独立放宽规则。

### 2. 建立规范目录并迁移定义

1. 先迁一组代表材料：Iron、一个气体、一个带组成的合金、一个木材、一个有意停注的条目；验证命名、相态与引用能表达后再迁余下目录。
2. 不在声明常量初始化时执行注册。建立材料对象和按键链接的固定流程，避免读取 `Materials.X` 自动在任意生命周期安装整个目录。
3. 逐类迁移生成目录的工厂调用；保留生成声明与已知来源，不假称历史生成器存在。一次性转换脚本和原始 GT6 源码放 `work/local-tools/`。
4. 将补充材料、粒子、Magic、反物质、染料和必要的材料组纳入同一身份规则；内部类型可以不同，但不能再形成不受校验的注册入口。
5. 用目录安装顺序和稳定链接顺序确保可重复结果，不以 `HashMap`／`HashSet` 的遍历顺序分配配方或附属身份。

交付：所有内置身份由规范目录安装，旧符号门面仅引用已安装的同一对象。

### 3. 收敛关联表与历史缺失行

1. 按事实所有权逐项迁入规范声明：组件、加工目标、基础形态集合、燃料、分解能力；迁一项即停止旧表写该字段。
2. ID 与名称都存在的历史表先验证二者指向同一材料；不能继续“ID 优先、名称兜底”掩盖矛盾。
3. 对停注材料清除仅供当前运行目录的无效行；若保留为历史输入，使用显式停注状态并由导入／校验阶段处理，不送入运行时解析器。
4. 断言引用目标存在、数量与 divider 合法、必要字段完整；不要过滤掉无效组件后继续注册一个残缺配方。
5. `postInit()` 中最终补的静态事实应迁回目录或明确的最终派生阶段，保证消费者读到的是最终状态。保留必要平台装配顺序。

材料翻译文本与材料物理事实各有自己的唯一来源。现有 lang 保持翻译权威，目录派生材料语言键并验证覆盖；若以后生成材料专属语言子集，必须先确定文本归属和资源合并方式，不能覆盖整份大型语言文件。

### 4. 关闭旁路并同步契约

1. 以调用方清单证明生产代码不再通过旧工厂隐式安装材料。
2. 只读门面继续返回规范对象；删除没有消费者的重复字段与二次初始化代码。
3. API 中的 `GTMaterial` 当前标记为内部模型，但仍位于 API 产物；对签名和生命周期变化执行 A，公共附属声明与访问器保持兼容或提供明确迁移。
4. 更新现有 API、content、engine、runtime 包文档中的实际注册职责；新阶段真正落地后再将说明从“计划”改为“当前实现”。

## 完成、拆分与兼容边界

建议依次交付：安装核心与负例、代表材料目录、全目录迁移、关联静态事实迁移、旧入口关闭。每一批保持原有消费者可用；尚未迁移的字段标明唯一写入者，避免双写。

完成条件：新增一种普通内置材料只增加一处领域声明；所有活动身份只安装一次；未知引用和未声明冲突能失败；01 的身份／数量对照通过。03、06 尚未迁移的复杂数据可以仍用旧表示，但必须通过规范目录关联，不能再各自决定材料身份。

本阶段默认不改变注册 ID 或存档格式。需要改变的历史特例作为单独兼容性变更交付；关闭入口不是删除仍被附属公开契约使用的能力。

## 实施结果（2026-11-07）

- 内置身份由 `content.material.catalog` 的七类领域声明统一安装；`MaterialDefinitions` 只收集、排序和建立稳定键索引，读取符号门面不会触发注册。
- `MaterialRegistryState` 在修改名称、ID、别名和全量集合前完成身份校验；sentinel、内置、历史和附属安装使用明确模式。`GTMaterialRegistry.init()` 依次完成定义、引用校验、链接、附属回调、最终角色和不可变视图发布，重复初始化幂等，任一阶段失败后后续访问继续失败。
- `MaterialFactories` 已删除；生产代码不再通过旧工厂隐式安装材料。`Materials`、`GT6Materials`、`ImportedMaterialData`、粒子、反物质、染料和材料组符号返回同一规范对象。
- 组件、加工目标、形态集合、燃料、分解权限和角色事实已经进入规范声明或明确最终派生阶段；`postInit()` 只校验 READY，不再补写静态材料事实。
- API 1.4 新增定义目录、类型化 metadata、材料 tag 包含关系和附属替代组声明。附属只能写入自身命名空间；未知 tag／组、包含环、组环、未知材料和跨所有者冲突在 READY 前失败。
- API 1.5 在过渡层增加类型化 `MaterialProcessKey`／`MaterialProcessesView`、附属 process 声明和 `MaterialFormRulesView`。smelting、crushing、pulverization、fuel、ore processing 与工具查询拥有独立 Helper；旧 `GTMaterial` getter／setter 暂时保留并标记弃用，现有下游仍可直接编译。`MaterialFacts` 已删除，原 34 项扁平数据先收敛到分组对象。
- API 1.6 进一步把主声明收敛为 `MaterialDefinition` 的身份、展示、物性、基础属性和来源五项；工具、组成、关系和处理规则进入 `MaterialInfoDefinition` 与独立的 `MaterialInfoRegistry` 索引。`MaterialInfoTool.forAddon(addonId)` 提供类型化注册，`GTMaterial#tool()` 是冻结工具索引的只读快捷方式。metadata、tag、group、form 和 process 的索引在 READY 后不可修改；process value 由调用方持有，Javadoc 规定注册后不得动态修改，宿主不强制深度冻结。
- `MaterialCatalogView` 在 READY 时发布不可变视图；旧宿主实现通过默认方法明确报告不支持。材料翻译仍由现有 `assets/gt6ce/lang/*.json` 维护，并增加全部非组规范材料的英中语言键覆盖测试。
- 01 旧快照与当前最终状态有 87 个材料属性差异，全部来自世界生成和石材角色的最终派生 flag：79 个增加 `GENERATE_ORE`，3 个增加 `GENERATE_ORE` 与 `GENERATE_ORE_PROCESSING`，5 个增加 `STONE`。这些 flag 在旧流程中也由 `MaterialRoleFlags.apply()` 于物品注册前写入；02 将其前移到 READY 前的最终定稿。双平台物品、方块形态、配方、tag 和代表案例投影仍与 01 基线逐文件一致，注册 ID、存档格式和运行行为未改变。
- 检查集 D、F、J、A、C、G 均已通过；API 104 个 JUnit、core 99 个 JUnit、API 契约和 READY 前失败路径全部通过，双平台各 79 个 GameTest 通过。生产资源与打包配置未改，因此本阶段未执行 B；客户端手工场景不属于本阶段完成条件，未执行 M。
