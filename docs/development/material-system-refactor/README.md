## 问题与目标

当前材料注册有不同约束的入口，物品成分采用最后写入者覆盖，批量遍历与运行时查询又不包含相同的数据。回收和分解生产端各自补判定、换算和特殊分支，导致同一事实随注册顺序、查询路径和版本变化。

目标是让每类事实只有一处维护位置，让消费者共用解析结果和计算规则：

```text
材料规范目录 → 注册校验与引用解析 → 材料属性、形态和分解规则
物品成分声明／派生候选 → 冲突裁决 → 同一版本的成分快照
材料规则＋成分快照＋输入状态 → 回收／分解计划 → 机器与版本适配
```

“单一来源”指一个字段只有一个权威定义，可以按材料类别拆文件；物品的成分与材料自身的化学组成是两种事实，不能合成一张表。“统一提供者”允许不同机器的工艺规则不同，但不得各自重新解释成分和回收授权。

材料分类／tag、替代组、可成形态、获取途径和矿物处理图一并考虑，主材料保持身份、属性与 flag 的简洁模型。拟议 API 的边界、接口和快照语义见[设计提议 0001](../../decisions/0001-material-data-api.md)；来源与图从有效配方及世界生成配置派生，不另建一套产物事实表。

## 共同实施约束

1. **正确性依据**：现有 [parity 决策](../../decisions/parity/README.md) 优先；其次是固定 GT6 提交 `3703e40308c8c030763fd6297dea8b210d2a77b1`，再参考本仓库 NeoForge、Forge 实现。当前快照只证明现状，不自动成为正确答案。没有依据的差异保持待裁决，不通过更新快照掩盖。
2. **源码层**：纯声明和内容事实放 core 的 `content.material`／`content.recipe`；通用计算与解析放 core 的 `engine.material`／`engine.recipe`；`ItemStack`、游戏注册表和原生流体适配留在共享 Minecraft 层。公开契约属于仓库内 `api/`。不新建平行的整套框架。
3. **身份兼容**：默认保留材料数值 ID、注册名、物品／流体 ID、配方身份和持久化单位。附属材料沿用当前命名、所有权和宿主分配 ID 规则；动态附属 ID 不作为跨环境稳定存档标识。需要改变身份或已公开签名时，先列影响与迁移，再修改。
4. **生命周期**：计划 02 明确材料定义、链接和定稿的实际调用边界；计划 04、05 单独处理标签／配方重载。不得把可重载的成分和配方永久冻结在首次类初始化中，也不得擅自提前拒绝现有合法附属链接回调。
5. **渐进替换**：旧门面只转发到新权威，不继续存一份可变事实。允许测试中比较旧／新计算；生产中每个已迁移配方族只能有一个写入者。保留的兼容入口要列消费者和退出条件。
6. **数据与生成**：选择 Java 类型化声明作为本次规范目录的起点，复用现有构建，避免为第一步额外引入解析器。一次性 GT6 抽取／导入脚本放 `work/local-tools/`；共享目录校验优先使用 JUnit。以后确需长期投影工具时，放 `tools/<scope>/` 并附 README；其输入为已提交的规范数据，不依赖未记录的本地上游 checkout。详见[文件归属](../repository-layout.md)和[资源指南](../../architecture/resources.md)。
7. **范围**：形态和材料去留逐项审计；有消费者的内容不会因为“生成量大”自动删除。损坏物品、多组件热回收、燃料灰烬和熔炼授权先核对工艺依据，再确定规则。

## 检查的使用方式

所有检查从仓库根目录执行，具体命令、注意事项和报告位置引用以下现有文档，不在每份计划重复维护命令：

| 检查代号 | 当前入口 | 适用情形 |
| --- | --- | --- |
| D | [文档与路由检查](../../../tools/validation/README.md#命令) | 本组文档、路由与检查文档一致性；还需人工检查新增文档的相对链接和锚点 |
| F | [format](../validation/checks/format.md#运行命令) | 每次生产代码或测试代码改动；不得扩大排除范围 |
| J | [junit](../validation/checks/junit.md#运行命令) | 纯计算、目录校验、数据归一化；涉及 API 时包含相应模块 |
| A | [api-contracts](../validation/checks/api-contracts.md#运行命令) | 改变公共签名、异常、契约或生命周期；版本变化还需同步 API 文档与提交说明 |
| C | [compile](../validation/checks/compile.md#运行命令) | 两节点生产编译，含 core 到游戏层的调用变化 |
| G | [gametest](../validation/checks/gametest.md#运行命令) | 两节点运行期注册、查找、拒绝、消耗与重载 |
| B | [assemble](../validation/checks/assemble.md#运行命令) | 生产资源变化与最终交付；检查发行包不含测试和临时文件 |
| M | [manual-ingame](../validation/checks/manual-ingame.md#运行命令) | tooltip、客户端配方展示、实际操作与机器界面 |

实施时先按[验证与验收流程](../validation/README.md#工作流程)路由实际改动路径，再取该分计划检查集的并集。路由未自动包含某个运行场景不构成省略它的理由。G 应分别执行两个节点，确认实际执行用例数和失败数，不能只看 Gradle 退出码；C 不代替 G。

01 已在共享 `minecraft/src/test` 接入材料领域 `MaterialBaselineTests`，复用 `gt6ce` namespace 与现有模板。后续测试继续按领域扩展，不新建 per-issue JavaExec。现有 crafting TSV 只能表达其已有级别，不能直接承载机器回收／重载断言；涉及这类场景时使用材料领域测试，只有模式稳定后才提炼案例表。

## 每个阶段的交付记录

每个小变更需给出：改动文件、已替代入口及消费者、行为差异和依据、执行检查及结果。原始 dump、日志、对比脚本和截图放 `work/material-system-refactor/`；经人工确认的期望数据才进入相应 `src/test/resources`。跨平台的长期结论按 [integration](../../integration/README.md) 格式整理，GT6 行为偏离写入 parity。

验收记录必须分别写“执行且通过”“执行但失败或阻塞”“尚未执行”，标明节点、样例、首次启动／重载／附属环境覆盖。任何未裁决差异不能计为通过；外部环境阻塞时保留具体原因。
