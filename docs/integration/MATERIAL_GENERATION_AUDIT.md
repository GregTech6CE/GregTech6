# 材料生成链与当前源码核查

日期：2026-10-19；基线 `549bf3076`。本轮承接属性表排版时暴露的再生成失败。原版只读来源是 `C:/Dev/gregtech6-master/gregtech6-master/src/main/java/gregapi/data/MT.java`，作者 GregTech-6 Team / Gregorius Techneticies，保留 LGPL 来源。

## 差异与来源

原有自检把声明数固定为 1056；旧中间快照已经有 1058，而当前五个材料表共有 1062 条声明：元素 172、化合物 570、矿物 125、石材 71、木材 124。这是定义行数量，不是游戏里唯一材料实例或物品注册数量。

从原版重新运行当前解析、发射和分表步骤到 `work/` 后确认：

- 旧快照有 55 条元素表达式未跟上当前修复，包括气体元素的原子数据、部分元素的零质子／中子及错误粉末工厂。现有 transpiler 已能从原版生成当前表达式，问题是中间快照未更新、分表器遗漏 `AtomicProperties` 导入。
- 旧快照有 106 条木材表达式仍把原版 `woodnormal` 尾部 RGB／工具参数当成温度和密度。当前 transpiler 已正确生成 `woodNormal`；另外需要保留已采用的 Magic、Cinnamon、Lime、Ash 四项，及当前 holder 末尾顺序与引用门面前置顺序。
- 火药、炸药的原版声明（MT.java:1309–1310）明确带 `EXPLOSIVE, FLAMMABLE`，当前 Java 已采用这两个标志，但生成器没有带上。现在从实际原版参数确认标志后输出；若来源的标志改变则报错，不静默填造。

不把这一小组修复推广为所有材料属性都已对齐。其它工厂继承、标志与加工消费仍由整体审计队列继续核查。

## 实际修改

更新 `tools/generated/materials-source.java.txt` 为本次原版解析得到的中间结果。分表器按实际使用添加原子数据导入，并明确维护四项后补木材的已有初始化／引用顺序。两个爆炸物的已采用标志回到生成器。

`modular_materials.JAVA` 与矿石资源工具的材料／世界生成读取入口改为真实共享 core 源码。原生资源输出路径及完整 transpiler CLI 的其它行为没有迁移；不能据此直接运行旧工具覆盖资源。

自检使用五组独立声明数、七文件逐字对比，并改用当前矿石工具公开的引用表达式。输出放在已验证属于仓库 `work/` 的独立目录，保留 Windows 工作区 ACL，结束时只清理自建目录。

## 验证与边界

先在临时目录完成从原版输入生成七个文件，全部与当前生产 Java 逐字相同，才更新中间快照。随后 `python -m unittest tools.tests.test_modular_materials` 的三项检查通过（约 4.4 秒）：快照再生成、标识符转换保留字符串／注释、现有世界生成标识符引用的材料解析。

七份生产 Java 相对基线完全不变，字段内容、排序和上一批列对齐都保留。没有构建、原生编译、游戏、存档重启或推送。原版生成过程中另报告的 14 项矿物处理跳过仍是单独的导入缺口；未应用新矿物处理文件或生成模型，也没有把标识符检查当成所有世界生成字符串、矿层行为或配方完整性验收。
