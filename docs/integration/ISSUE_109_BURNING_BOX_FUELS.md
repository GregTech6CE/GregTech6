# Issue #109：燃烧室燃料与连续供热

2026-10-25，修复起点 `1101f6426`，提交分支基于主线 `9bdd17034`。读取当前仓库 18 个开放 issue 后，优先处理 [#109](https://github.com/GregTech6CE/GregTech6/issues/109)：它影响液体、气体和流化床燃烧室的实际供热与生存进度。

## 根因和修复

- `FluidBed` 只有空表和消费者，没有内置燃料注册。恢复原 `Loader_Fuels:37–43` 的 11 种材料、5 种形态；方解石为 648／72／18／8／1 mB，热量和灰渣使用原始剂量。原有通用材料炉时数据不完整，因此原燃料参数单独保存，不改全局材料。
- 柴油、煤油、航空燃料等原本同时属于 `Burn` 与 `Engine`，现有导入只写入 `Engine`。补充原 `Burn`／`Gas` 声明，按实际流体身份去重，保留两个配方表各自的热量，缺少可选流体或声明的出液时跳过。
- 液体／气体每 tick 只补一份燃料，低热量燃料在高额定输出机器中会立即熄火。现在补足两份额定输出的热储备；补燃失败时，只在剩余热量不足一次额定输出时熄火。流化床保持每 tick 至多一份。
- 低功率流化床原罐仅 `rate × 10`，例如铅炉 160 mB，放不下粉块的 648 mB 方解石。改为原始 `max(rate, 配方表最大输入量)`，默认至少 1000 mB；读取旧 NBT 时也提高容量下限，保留已有流体和更大容量。
- 扣料使用现有 `RecipeInputs` 先计算后提交；按计划的实际消耗量扣除 long 储罐，避免原生 int 配方视图截断更大的保存量。零有效热量、溢出和完全不消耗资源的扩展配方不扣料、不产热。沿用已有满灰阻塞策略。

来源、作者、许可证与七份只读原源码的 SHA-256 见 [来源记录](../../core/provenance/issue109-fuel-recipes-20261025.json)。

## 验证范围

新增共享 `BurningBoxFuelRegressionTests`，命名空间 `gt6ce_burning_box_fuels`：实际注册炉与锅炉的弱燃料连续供热；10 种液体燃料的独立 Burn 热量；末份余热；零有效热量；煤的五形态方解石／灰渣守恒；满灰阻塞与抽灰恢复；旧容量 NBT 加载不丢液体；三类炉消耗超过 `Integer.MAX_VALUE` 的保存流体时不截断存量。

这 8 项已接入现有 `Focused issue regressions` 工作流，报告检查器要求正确方法名及模板命名空间下的全部通过记录，缺失、失败、跳过或零发现均不放行。集中 Python 检查器单测 59 项通过；工作流沿用原有 `main`／`fix/**` 推送及手动触发规则。

最终结果：主线 `9bdd17034` 上的 `:core:check` 通过；Forge 1.20.1／47.4.20 和 NeoForge 1.21.1／21.1.243 各 8 项集中原生 GameTest 全部通过，报告逐项核对无缺失、失败或跳过。两版均实际注册 55 条流化床和 48 条补充 Burn／Gas 配方，拒绝数 0；5 条可选流体声明因未安装对应流体而跳过。见[验证回执](verification/issue109-burning-box-fuels-20261025.json)。

构建使用本机缓存离线验证，`directCoreClasspath=true` 直接加载共享核心输出；最后 Forge 增量仅额外跳过阻塞的外部证书预检，未修改仓库构建配置。首次 Forge 的 5／6 结果保留：测试先拍快照、再首次查询能力时触发覆盖板延迟初始化；初始化移到快照前后，完整状态不变断言通过。
