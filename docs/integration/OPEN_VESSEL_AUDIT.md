# 搅拌盆、浸洗盆与榨汁机续核

2026-10-22，第九十九批，基线 `f260e3e6e`。读取20份原版来源、22份当前来源及其中28份共享平台投影；作者／许可证头、七种注册、有限源码条件及完整排版证明见[回执](verification/open-vessel-audit-20261022.json)。本批只核对和整理源码，未改变玩法。

## ALIGN-309：自动输入缺少同物品只占一个输入格的限制

原搅拌盆和浸洗盆都提供六个输入格。`canInsertItem2`先拒绝产物格，再扫描已有输入；发现同物品时只允许已有的那一格，最后才检查配方输入身份。木盆继承浸洗盆的这条逻辑，原06父类也把原生按面插入回调转到它。

当前共用 `ItemStackHandler.isItemValid`只检查输入格范围和 `recipes.containsInput`，对外handler的插入仍委托这个库存，没有跨输入格重复检查。前提为0号格已经有相同的普通有效物品、候选格为空且该物品仍被配方接受；原对1～5号格的自动准入拒绝，当前准入通过。三种实现家族的18项槽位角色是源码条件展开，不是实际漏斗操作。

这项只比较遵守原生按面准入的自动输入。原手动流程另用 `ST.move`，不能仅凭循环名字便认为也执行完全相同的过滤；完整手动取放和第三方绕过规则没有在这里验收。

## ALIGN-310：普通排液开放输入液，且产物选择不再轮换

原Root的两个公开 `drain`重载，分别以指定流体或null查询 `getFluidTankDrainable`；06再转到盆类的 `getFluidTankDrainable2`。盆类仅返回 `mTanksOutput`，不会从 `mTanksInput`返回液体。

原手持容器交互却会分别尝试产物罐和输入罐，因此“原能用瓶子拿走输入水”不能用来证明普通自动排液也应开放输入罐。当前普通handler的两个drain都遍历 `allTanks()`，其内容依次是产物罐和输入罐；两版本机能力注册确实把这个handler交给外部。

例如没有产物液、输入罐有1000L合格水，普通自动接口请求1000L：原找不到可排罐，当前可以返回输入水。这里是原生查询／容器代码的推导，不是管路实测；没有覆盖板或外部能力改写时才套用这个例子。榨汁机本来没有流体输入罐，不属于这项输入液暴露。

对未指定流体的查询，原还以 `SERVER_TIME/20`轮换产物罐的起点，当前固定从产物0开始。有两个／三个非空产物罐时，五个起点相位中分别有一／两个与当前不同。原只返回本次选中的一个罐，并不是一次取遍全部；没有据此宣称当前一定堵塞或固定降低吞吐。

## ALIGN-311：加工产物的储量与物性门控未完整保留

原搅拌盆／浸洗盆在已有产物液的罐中，拒绝继续加工到 `stored >= max(1000, 1 + nextBatch)`。这是针对加工的暂停门槛，名义罐容积仍为8000或4000；不能称其实际容量只有一桶。比如999L可以再接受一份250L到1249L，之后再判断是否暂停。

当前 `canOutput`只在juicer分支保留这项储量门槛，六种盆类通过同液和剩余容量的模拟检查即可继续。以已经1000L、下一份250L且其它材料／产物条件均允许为例，原暂停，当前4000／8000L盆仍通过。回执的六种盆×四个已有量，是24项源码条件，不是实际运行配方。

原在已有产物液时还检查温度、轻质液体，以及搅拌盆的SIMPLE、浸洗盆的gas条件；榨汁机也有温度／轻质检查。当前 `canOutput`没有相应检查。实际读取的 `FluidTankGT.fill`只处理身份、容量和模拟／执行，并不消费它保存的maxTemperature等物性字段，因此不能把SIMULATE成功当成这些物性已经通过。

这些物性缺口限定原门控生效的非空、兼容产物罐；原空罐也有绕开某些检查的分支，不能把原代码说成完整危险保护。实际哪些配方能提供相应产物、温度／密度映射及最终加工结果仍待核，本批不启用危险或恢复可能丢弃产物的旧路径。当前先验证容量再扣料的保护保留。

## ALIGN-312：四种浸洗盆的固体显示路径不同

原不锈钢／木浸洗盆在没有液体但有材料显示时，都调用 `OreDictMaterial.getTextureDust()`；该方法实际使用blockDust纹理。两个桌式子类继承相应路径。

当前 `ProcessingToolRenderer`只对 `mixing_bowl`前缀使用材料粉末平面。四种 `bathing_pot`变体进入后面的 `ItemRenderer.renderStatic`，渲染完整物品模型。Forge／Neo客户端均把此渲染器注册给真实的PROCESSING_TOOL实体，不能因方块自身也有静态模型便忽略这条消费者。

显示成员的选择还有政策差异：原浸洗盆扫描6～0号格，仅含第一个产物格和输入；当前从11～0选择，额外产物格也会显示。本批不为了字面一致隐藏这些产物，也没有给出真实客户端像素结论。既有008搅拌盆发光材质和050动态Bath配方不因这次读到普通渲染／静态配方就关闭。

## 已有内容与既有合同扩围

- 七种身份及名义容量对应原注册：木盆4000，陶瓷搅拌盆和不锈钢盆8000，榨汁机输出1000000；桌式继承对应家族。普通物品／流体能力、输入准入、手工处理及世界保存／读取已有，不报整套容器未实现。
- 榨汁机配方目录是零流体输入、一个流体输出，当前fill即使先通过通用物性检查也没有输入罐可写，正常返回0；不能从`acceptsFluid`函数存在就误报榨汁机能被灌入任意液体。它也不开放物品自动化，固体产物走玩家给予路径。
- 世界保存包含物品和流体；当前普通拆除掉出物品，原盆类也没有将储液字段写入块物品的专用覆盖。本批没有把液体未随普通掉落保留报成新缺失，独立重启、盖板、外部收获改写和旧档继续待验。
- ALIGN-172补实际发送方：原Root的`updateAdjacentInventories`确实遍历六面广播；浸洗盆／榨汁机成功加工以及搅拌盆的流体容器灌入分支有调用。当前`changed`标脏、发块数据更新，没有同一专用广播；不扩大成“每种原手工加工分支都会广播”，也不推定物品永久不传输。
- ALIGN-308扩至三种容器家族：原搅拌／浸洗／榨汁使用250／1000／10000基础除数后仍经原疲劳倍率函数，当前直接交给原生消耗。上批两工件四条目已重新核摘要，无新增javap。浸洗原最小功率1、零功率最终配方和其它极限另待核，不在本批修正。

雨水入口、普通气候公式和雷雨倍数已有；原全局SERVER_TIME与当前保存的世界时间、完整原生天气／遮挡条件、配方优先级、工具费用、主动电动搅拌以及流体物性的其余分支继续核查。本批不从方法名或名义罐容积推定全部一致。
