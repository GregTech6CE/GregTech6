# Machine and functional-block audit continuation

User priority: machines, functional blocks, actual missing functionality, and multiblock cross-chunk lifecycle. Baseline main `4049d81b8` passed both builds and 114 selected native cases. The prior bounded CI pass is not completion of the broader audit.

## Machine menu lifetime

Basic machines and both apiaries checked only the removed flag; hopper and queue providers inherited a menu that checked only non-null inventory. Native server container handlers rely on `stillValid`, so distant or wrong-world viewers could keep a menu valid. The new guards require a live original block entity, same world, at most eight blocks, and a loaded owner chunk before querying its identity. Client null-owner handling and inventory transactions are unchanged.

Five shared native tests use registered blocks and their real menu providers. They cover nearby and exact-boundary players, too-far and other-dimension players, removed/destroyed/replaced owners, and the replacement's own valid menu. This tests validity predicates, not a network disconnect or actual automatic GUI-close flow. Selected totals become Forge64 / NeoForge60; exact-commit native execution is still required. No test substitutes simulated chunk availability for real unloading.

## Cross-border neighbor reads and mixed layout alternatives

Six BasicMachine adjacent I/O paths now check loadedness before reading the neighbor: primary and auxiliary energy polling, automatic item input/output, automatic fluid input and fluid-output target lookup. This preserves current transfer/filter logic but prevents absent chunks being force-loaded or treated as empty air for item ejection. Native tests place a real registered large centrifuge at positive and negative remote chunk borders, form its complete loaded shell, and call its native tick; a second test checks unavailable I/O retains stock and a subsequently loaded chest receives exactly that stock. These are no-force-load tests, not evidence of a complete natural multiblock unload/reload cycle.

PR #93 permits plain-block/GT-part alternatives. Validation previously returned only a boolean and then bound using the first branch's metadata: a stone alternative could be cast to a missing port, or a port alternative could remain unbound. Validation now retains the actual matched branch for binding/designs, including only complete repeat copies. Two native tests use the public declaration converter and an isolated layout override on a real controller implementation, exercise both choice orders, plain/port transitions, role isolation, incomplete repeats and invalidation/reformation. The layout override is an explicit fixture boundary, not a mock of matching/binding logic.

The earlier menu commit `9d93a848e` passed both main workflows and all 124 native cases. These four new shared tests raise selected totals to Forge68 / NeoForge64; their exact-commit native execution is pending at authoring time.

## Presence-only fluids, capability lifetimes, lockers and native chunk lifecycle

Textual zero-mB inputs now retain native fluid identity via a positive representative plus explicit presence indexes. Matching checks original tank snapshots without reservation, drain, order dependence or parallel multiplication; native addon read/add/find, overlay removal matching and recipe viewers preserve the metadata. Native zero-sized FluidStack inputs remain invalid because the loaders erase their identity; the SDK offers a positive representative plus presence indexes instead. Seven native cases cover these paths and preserved positive-kept behavior. Direct fuel converters on Burn/Gas/FluidBed/Engine/Hot reject presence rows explicitly; barrels skip them while ordinary fermenters accept them. Configurable heat exchangers reject matching presence rows without draining or purging their fluid and can still select an ordinary fallback. These are documented compatibility boundaries, not claims every legacy specialized converter understands presence semantics.

Forge's LazyOptional.lazyMap does not forward invalidation. Derived fallback cover capabilities now use a per-owner capability/face cache, forwarding original lifetimes and preserving dynamic filters. Five Forge-only tests cover real drawer side remapping, rotation/removal, unresolved handles, separate item/fluid lifetimes, and cross-face/same-key invalidation reentry. Callback-installed newer sources take precedence over the superseded outer snapshot; stale outer lookups return empty rather than evicting or impersonating the newer source. No global owner cache or NeoForge capability changes.

Ordinary locker interaction now requires the front/main hand and validates each stored item with the native canEquip rule before swapping that slot. Two shared tests preserve nonfront/offhand inventories, valid equipment round trips, and intentionally injected invalid saved equipment without claiming ordinary gameplay produces that invalid state. Charging lockers remain a missing family, not silently folded into ordinary lockers.

One new native lifecycle test uses a real registered centrifuge spanning two remote chunks, observes actual unload events plus removed old block entities, then reloads only the controller and finally the shell. It asserts native inventory/energy restoration, safe incomplete validation without forced neighbor loading, and fresh port rebinding. It uses FULL/UNKNOWN tickets rather than forced tickets; a forced controller would keep neighboring chunks loaded and invalidate the test premise. Completion/failure cleanup is attached to the actual GameTestInfo. This single-JVM staged native unload/reload test is not an independent process restart, natural ticking partial-unload scenario, multiplayer stress test or old-save compatibility proof.

Required totals for this verification branch are Forge83 / NeoForge74. Local Java17 core compilation and 121 independent core contract processes pass; Python language/source/evidence checks pass. New native cases still require exact-commit CI. Earlier tests' green reports do not certify these additions. Future batches use a temporary verification branch, merge only after both loaders pass, and delete the completed branch; the previous main test-setup failure was corrected rather than skipped.

## Verified checkpoint and behavior-machine structure validity

Verification branch `679a89df2` passed [both builds](https://github.com/GregTech6CE/GregTech6/actions/runs/39894073920) and [all 157 selected native cases](https://github.com/GregTech6CE/GregTech6/actions/runs/39894073918). Both lifecycle logs observed two actual unload events, three removed old entities, controller-only reload with shell unavailable, then fresh rebinding and exact seven-diamond/512-RU persistence; cleanup removed the listener with zero forced tickets. These facts establish the staged registered-centrifuge test only, not every multiblock family or independent JVM restart.

The separate addon BehaviorMachine executor had the same unguarded neighbor energy reads and primary-branch binding assumptions. It also exposed a cached formed flag to retained port handlers, permitting transfers after a required cell changed but before the next controller tick. It now validates on port access, retaining actual matched choices, and fails closed during reentrant binding validation using a finally-reset guard. Three native tests exercise registered sample behavior machines with an explicitly isolated layout/resolution cache, matched fixed/repeated alternatives, rejected retained item/fluid transfers before a tick, reformation, removed-owner rejection, reentrant bind callbacks, and real unavailable-neighbor polling. These additions require their own exact-commit native pass (Forge86 / NeoForge77); the 157-case checkpoint does not certify them.

A suspected layout-to-null orphan transition was rejected as unsupported: published overlays require a frozen existing base definition, reject an empty layout, and removal restores that non-null base. No speculative production patch was added for a transition possible only through test reflection.
