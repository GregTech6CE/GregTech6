# 筛选台的输入数量、自动化和操作者

2026-10-22，第九十七批，基线 `e7d676234`。核对12份原版来源、15份当前来源及其中20份共享平台投影；原作者／许可证头、摘要、有限源码条件及排版证明见[回执](verification/sifting-table-audit-20261022.json)。这是手工筛选台 `sifting_table`，与上批修复的粉末筛粉漏斗 `dust_funnel`分开。本批只审计和整理排版，未改玩法。

## ALIGN-301：原单件工作格变成整组插入

原 `MultiTileEntitySiftingTable`有13格，`getInventoryStackLimit()`返回1。顶部没有正在加工的物品时，先检查 `canInsertItem2`，再通过 `ST.move(玩家库存, 本机, 手持格, 0)`移动；这个具体重载会用目标库存上限裁剪数量。不能仅因外层默认移动上限64，就认为原筛选台收64件。

当前 `ManualToolBlockEntity.interact`在空工作格且找到配方时，直接 `work = held.copy()`；生存玩家手持数量随后置0，整组成为台内待加工物品。两版都使用这个共用流程。

| 符合配方的生存手持数量 | 原本次收取 | 当前本次收取 |
| ---: | ---: | ---: |
| 1 | 1 | 1 |
| 2 | 1 | 2 |
| 16 | 1 | 16 |
| 64 | 1 | 64 |

表格是上述分支的数量推导，不是实际玩家测试；前提为工作格空、同一份已被接受的配方。原与当前都声明16GU、144刻的菌丝土筛选行，当前还经过生成配方解析器；本批没有验收最终配方表、其优先级或实际产出。这里报告插入数量不同，不把“收走整组”写成物品已经丢失：当前有潜行空手取回和保存／拆除内容路径。

## ALIGN-302：原被动物品库存没有当前内建入口

原07父类继承06，06实际实现原生 `ISidedInventory`，05提供库存。06的原生方法会调用筛选台的 `getAccessibleSlotsFromSide2`、`canInsertItem2`和`canExtractItem2`；不是仅声明了一组没有消费者的槽号。

筛选台六面都可访问0～12格，只有0号格允许输入匹配物品，1～12号格允许提取；库存上限另为1。78个“面／槽角色”记录只是源码角色展开，不是78次漏斗操作。原没有凭此成为无人操作的自动加工机，玩家加工门控仍存在。

当前工作物品和产物保存在 `work`与十二项 `NonNullList`中，但具体实体直接继承原生 `BlockEntity`，没有实现原生容器接口、物品handler或Forge能力重载。Neo的实际实体注册能覆盖该方块，却没有对应物品能力提供者；同文件里其它设备的能力不能替代它。项目自己的 `NativeItemInventories.at`在两版查询原生物品能力，也不会仅因有`work`字段就读取它。

另对共享与两版原生主源码1251文件建立引用摘要，定位实际 `MANUAL_TOOL`／实体引用和能力附着入口，配合具体类与注册器阅读；这个搜索不是功能验收，也不证明第三方永远不能加能力。确认的是当前项目缺少原被动进出料合同。本批不添加第二份库存，也不改其它设备的通知链。

## ALIGN-303：操作者集合与继续操作条件不同

原每5刻在工作状态下遍历 `UT.Entities.getPlayersWithLastTarget(this)`。工具函数读取按玩家分别记录的 `PLAYER_LAST_CLICKED`；原交互事件实际更新这个表，集合可含多名玩家。它检查存活、同世界、最近点击的坐标，以及普通玩家6格距离；创造玩家绕过该距离。没有在这里做“仍瞄准顶面”的射线检查。

当前实体只存一个 `siftingPlayer` UUID，后点击者覆盖前一名；每5刻只查这名玩家，还检查8格平方距离、5格射线命中当前块的顶面，不符合便清除UUID。因此多人贡献进度和转开视线后继续操作的条件都不同，不能说只是原玩家列表换了一个字段名。这里不把代码中的8格检查简写成“实际可在8格操作”，射线还有独立的5格限制。

原循环会在每名玩家前再次检查产物格；第一名已经产出时，后续玩家可能被产物挡住。本批没有按人数直接倍乘产量，也没有给出实测耗时。原与当前的普通急迫／挖掘疲劳公式另核：无效果用-1，低三档效果共16种条件的增量和门槛相同；高放大值的原六位裁剪／字节饱和等边界仍待核。
