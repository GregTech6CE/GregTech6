# 树脂采集袋与树洞对照核查

2026-10-22，第102批，基线 `75ed5e224`。上一轮 issues 修复属于已完成的实际进展；本轮返回持续全面核查与源码整理。新增 ALIGN-322–328，并补充 ALIGN-139 的具体宿主。累计328条正式记录，包含已修、扩展合同、保留策略和待验项，不是328个待修缺陷或完成百分比。

本轮依据17份原版文件、23份当前 Java、3份模型／状态资源及40份核心／平台源码视图。作者、LGPL许可头、源文件摘要、31段引用、10份复用且重新核对字节摘要的原生证据，见[回执](verification/sap-bag-audit-20261022.json)。原版来源仍只读。

## ALIGN-322：橡胶树洞的两种产物被拆成互斥分支

原 `MultiTileEntityResinHoleRubber.getResinItem` 返回一份树脂物品，`getResinFluid` 同时返回250份橡胶树脂流体。原采集袋一次成功抽取后，依次向液体槽注入流体、向物品槽加入物品；两步不是二选一。原树洞手动操作也先尝试灌装容器，然后在同次抽取中给出树脂物品和成功灌装的容器。

当前 `GTTreeHoles` 为橡胶指定 `item:gt6ce:rubber_resin`，枫树／彩虹树指定 `fluid:`。`TreeHoleBlock.yieldsItem` 和袋内 `collect` 都按这个字段选择互斥分支；橡胶能给物品，但不会同时向袋内液体槽注入树脂。手动点击橡胶树洞同样只走给物品分支。缺口不在流体名称的显示，而在产物合同与实际调用。

原袋还消费 `ITileEntityTreeHole` 接口，当前只接受相邻的 `TreeHoleBlock`。这也是接口适配范围的收窄；注册三种自家树洞并不能证明原接口扩展合同已经移植。

现有 Forge `SapBagTests` 明确把橡胶袋内液体为0当成正确结果。它验证的是当前互斥实现，不能用来证明原版对齐。本轮没有运行或偷偷改掉该测试；以后修复双产物时必须同步更正这一期望。

## ALIGN-323：采集袋放置朝向依据不同

原袋同时启用 `useSidePlacementRotation` 和 `useInversePlacementRotation`，09基类据此取点击面的反面，并通过水平合法面列表处理上下表面。它朝向自己挂着的树洞。

当前袋继承 `ShapedToolBlock.getStateForPlacement`，固定取玩家水平朝向的反向，未使用点击面。两种依据在斜角点击时可以不同；采集逻辑仍只检查袋自身朝向的相邻格，因此不能把“手工先设对朝向后能采集”的测试当作真实放置正确的证据。袋的扳手旋转路径已有，但不代替放置规则验收。

## ALIGN-324：公开流体接口属于当前扩展

原袋确实有8000容量的私有液体槽，也允许玩家拿容器取液。但它没有覆写06基类的公开槽查询：可灌／可排槽默认都是 `null`，槽数组为空；袋还禁止贴覆盖板。仅看到 `mTank`，不能推出原版管道可直接灌排。

当前 `SapBagBlockEntity` 实现 `IFluidHandler`，直接转发填充、排出、容量与内容查询。Forge能力及Neo专门能力注册均暴露它。这是明确的自动化扩展，不应继续用“GT6普通液体槽，管道可排”解释。该误导注释已经改正，能力本身按本轮核查范围保留。

原单物品槽的自动化是另一件事：原返回空可访问槽、拒绝自动输入和输出；当前袋没有对应物品能力入口。不能把公开流体扩展连带说成物品槽也已开放。

## ALIGN-325：有满载查询，但没有满载外观消费者

原袋每tick按液体非空或物品槽非空更新 `mFull`，变化时同步；渲染按此切换 `overlay` 与 `overlay_full` 三张纹理。

当前已有 `isFull` 和内容同步，但袋的方块状态只有四个 `facing` 变种，两层复合模型都固定引用普通 `overlay`，没有满载分支。已经有布袋的几何和着色，不代表有原版满载外观。本轮将 `isFull` 注释改为说明当前模型尚未消费该值。

## ALIGN-326：外观材料和物品堆叠数不同

原32736注册采用 `MT.Leather`，注册容器在未显式给颜色时把材料固体色写入默认NBT，07实例读取该颜色。当前布袋的着色入口直接取 Rubber。此处确认的是注册／外观颜色来源不同，没有把一个着色分支当作完整的材料含量计算。

原注册堆叠数是64，经注册参数、类容器字段和物品公开堆叠查询传递。Forge的 `simple` 工厂没有将袋列入64组，Neo默认物品工厂也使用16，因此两版袋都落在16。未修改已注册ID、堆叠数、配方或物品存档。

## ALIGN-327：选中几何对应，实体碰撞与公开抗性不同

原袋选中边界与当前基础模型都为 `[5,0,0]–[11,7,6]`，四个水平朝向的旋转坐标全部对应；复合模型两个子层也使用这个盒子。这是源码坐标推导，未调用实际 `VoxelShape`、烘焙模型或放置API。

原袋明确返回空实体碰撞箱，并声明放置时忽略玩家碰撞。当前注册没有关闭碰撞，`ShapedToolBlock` 仅为高级按钮、脚手架设例外，袋会把选中形状作为实体碰撞。外观尺寸正确不等于碰撞合同正确。

原袋注册硬度0.5、抗性3；普通未触发自身爆炸标记的实例经07／Root及方块上下文查询返回3。当前两版注册 `strength(0.5,0.5)`；沿[上一批已核实的原生属性和查询路径](UTILITY_PHYSICS_AUDIT.md)返回0.5。本轮复用的10份相关原生证据重新核对了工件、条目和反汇编文件摘要。没有执行爆炸，也没有据此推算破坏概率或半径。

## ALIGN-328：树洞检查时钟与树干谓词不同

三种原树洞都按基类持续运行的 `aTimer % 600` 在空孔时检查。当前 `TreeHoleBlockEntity.tick` 在满孔时提前返回，只有空孔时才递增自己的计数。因此取走树脂后，下一次检查的相位并不一定和原版一样。阈值60／250、除数260／560／420已有对应，不能据此判整个补充算法相同。

原树干循环停止条件写作“方块不是目标日志 **且** 元数据不是目标值”，因此只满足其中一项也会继续；当前按独立木种方块精确匹配。原条件存在可疑的宽松行为，应作为原代码政策与现代木种身份适配的区别记录，不能在排版时悄悄恢复它。树冠坐标和基础概率已有实现，完整世界中的生长、稀疏树冠、相邻区块加载与采集后相位仍待验。

## ALIGN-139 补充：袋和树洞原本都禁止覆盖板

原袋和三树洞都返回 `allowCovers=false`。当前袋／树洞的方块实体会得到通用后备宿主；除已另行排除的材料堆外，`EntityBlock` 会通过准入，普通板又不要求特殊机器控制器。这条路径没有保留它们原来的全侧禁贴策略。部分专用覆盖板仍有自身能力门槛，不能泛称每种覆盖板都可安装。
