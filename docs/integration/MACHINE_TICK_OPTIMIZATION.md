# 机器 tick 开销优化（2026-10-24）

用户提供四份 Observable 报告后授权实施。范围是锅炉、固体燃烧室、基础机器及其共用配方／流体／邻接能力路径；没有修改产汽率、能量包大小、加工进度算法、过载或爆炸阈值。

## 基线和证据边界

原始报告位于 `C:/Dev/性能分析`，每份约 201–204 次 tick。`rate` 是 Observable 用 `System.nanoTime()` 测得的单台 tick 平均耗时（纳秒），包含该次 tick 同步调用的邻接设备操作；各方块耗时合计不是完整服务器 MSPT。

最后一份 `2026-10-24--01.49.13.json`：18 锅炉合计 0.698566 ms/tick，20 固体燃烧室 0.546946，3 青铜洗矿机 0.471084，2 殷钢干燥机 0.264721。洗矿机 `(58,69,-33)` 为 0.461379 ms/tick，前三次同坐标约 0.003 ms。四份报告均没有方法调用栈，不能据此量化各方法比例。

## 已实施

- **锅炉视觉同步**：每 tick 仍完整计算产汽、冷却、排汽和安全条件；只在 0–31 档仪表值变化时请求客户端更新。初次区块同步及后续更新都发送独立 `gt.boiler_visual` 字节，通过原生区块追踪广播，避免锅炉走旧的全量 NBT + 手动附近玩家发送。存档 `saveAdditional` 保留完整数据；Jade 仍通过服务器提供实时数据。
- **保存与邻接通知分开**：基础机器的收能／进度、锅炉热量／冷却、燃烧室能量只标记存档。单次机器 tick 内的库存回调合并到 `finally` 收尾通知；tick 外输入输出仍立即通知。没有将所有通知延迟若干 tick，也未删除真实库存更新。闲置燃烧室不再无条件 `setChanged`。
- **配方候选索引与缓存**：精确物品第一轮查询使用按输入物品建立的稀疏索引，按原集合顺序选取。每张配方表最多缓存 16 组物品／流体身份及组件对应的候选列表，包含材料等价／颜色替代候选和空候选；不缓存是否成功的结论。数量、启用标记、催化剂、输出限制每次重新判定；动态及上下文提供者仍实时执行。公共配方集合的增删／迭代删除及标签重载会使缓存失效；原地修改已注册配方的输入数组须调用 `RecipeMap.invalidateLookup()`。
- **匹配工作区**：只使用可复用数量数组模拟候选扣料，不为每个失败候选复制全部 ItemStack／FluidStack 及组件。确定实际扣料时才生成独立剩余堆叠；保留重复输入、跨槽／跨罐、并行、催化剂预留和 presence 流体检查。修正同 tick 两次无配方查找。
- **自动输入输出**：输入满、输出空时先从本机状态直接返回。邻接能力按方向缓存，验证方块实体身份、方块状态及世界，结合 Forge LazyOptional／NeoForge BlockCapabilityCache 的失效机制。没有降低有效传输的每 tick 频率或改变吞吐量。
- **无变化流体写入**：相同流体、相同数量的 setFluid、重复 setEmpty 等不再触发库存回调；实际传输和身份清除仍通知。
